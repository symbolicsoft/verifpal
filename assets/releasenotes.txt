Verifpal 1.2.3/1.2.4 fixes a completeness gap in Verifpal's active-attacker
search for equivalence queries, reported by Mario Raso. In addition,
this update used an AI-assisted review in order to identify areas where
active-attacker search could be further hardened against potential
future regressions. Finally, attack trace narration was further improved.

Verifpal 1.2.2 adds an exciting new output format: HTML reports!
Verifpal can now output highly informative, self-contained HTML reports
that contain diagrams and other explanations of your analysis' results.
Try it using: verifpal verify --format html your-model.vp.  

Verifpal 1.2.1 makes improvements to Verifpal's attack trace narration.

Verifpal 1.2.0 makes authentication queries injective.

Verifpal's authentication queries used to ask a weaker question than their
name suggests. The old rule was simple: did the recipient end up using a
value that the named sender never sent? If the attacker forged something,
the query failed, which is correct. But if the attacker copied a message
the sender really did send in one session and delivered it again somewhere
else, the old rule let it pass. Nothing had been forged, so nothing was
reported, and replay attacks went unmentioned. The query now asks for more.
For every time the recipient accepts a value, the sender has to have sent it
a separate time. If Alice sends a message once and Bob accepts it twice,
that is a failure, even though the attacker made nothing up. This stronger
property is called injective agreement, and it is now the only mode Verifpal
offers. There is no flag to turn it off.

The code change was small. One test in query.rs had been throwing these
results away before anyone saw them, so we stopped it from hiding them and
reused the same test to label them instead. Attack traces now say "Attacker
replays" where they used to say "Attacker replaces", and the summary line
spells out that the sender sent the value once while the recipient took it
twice. We also taught the trace minimizer to try a replay on its own, so
these attacks shrink to the single step that causes them rather than
printing a pile of substitutions that had nothing to do with it.
Twenty-four test models flipped from pass to fail. We read every one of
those traces to confirm each is a copied message and not a false alarm.
They all fail only when two sessions are analyzed, which follows from what
a replay is: with a single session there is no second run to copy a message
from. That gave us somewhere to keep the old guarantees, so the models that
exist to prove a particular attack is not a forgery still prove it at one
session.
